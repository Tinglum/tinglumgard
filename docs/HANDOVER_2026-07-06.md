## 2. Live incident — found, diagnosed, NOT YET FIXED (do this first)

### Symptom
Customer report: order **EGG13063678** — "I ordered 30 eggs, only a few eggs went out, looks like a new order overwrote it."

### What actually happened (fully proven, not speculation)
1. Customer paid **1,600 kr total** (650 kr deposit 06-24 + 950 kr remainder 06-25) for **30 eggs** across 3 breeds (11 Jersey Giant + 10 Cream Legbar + 9 Maran + 300 kr Posten shipping). Confirmed via two email previews the user showed me (deposit-confirmed email and remainder-paid email), both showing all 30 eggs and matching the 1,600 kr total exactly.
2. **07-05, 10:14** — day-before "add more eggs" 30%-discount offer email sent (this is normal, scheduled).
3. **07-05, 11:20** — customer opened the add-more-eggs page (`app/rugeegg/mine-bestillinger/[id]/betaling/page.tsx`) and, using the quantity steppers, reduced Cream Legbar from 10→2 and Maran from 9→4 (confirmed: `2800 = 4000×0.7` and `3150 = 4500×0.7` — exact 30%-discounted unit prices for the *same* breeds, proving this was an edit of the existing lines, not new ones).
4. Submitting the form calls `POST /api/eggs/orders/[id]/additions`, which does a **full delete-then-reinsert** of `egg_order_additions` for the order — whatever the client submits becomes the *entire* additions set. Nothing merges it with what already existed.
5. Net effect: **8 already-paid-for Cream Legbar eggs and 5 already-paid-for Maran eggs were silently deleted**, with no new charge (none was owed — see below) and no warning. Order dropped from 30 eggs/1,600 kr to 17 eggs/977 kr while the actual money collected stayed at 1,600 kr — the DB now thinks the customer overpaid by 623 kr, but really they're owed ~13 eggs.
6. **07-06, 12:49–12:50** (today, delivery day) — customer opened "Min side" again. `GET /api/eggs/my-orders` (the **list** endpoint, not `[id]`) unconditionally re-sends `egg.order.deposit.confirmed.customer` for any order with a completed deposit, with no check for whether a confirmation was already sent. Because the order's rendered content had changed (fewer eggs), the email dispatch idempotency hash (`lib/email/queue.ts:55` — hash of `to_email|subject|html`) came out different from the original, so it wasn't deduped — a second, differently-worded confirmation email went out today. **This is what made it look like a brand-new order had replaced the original one.**

### Two distinct bugs, root causes identified

**Bug A (the actual money/inventory loss — highest priority):**
`app/api/eggs/orders/[id]/additions/route.ts:71-83`. The only guard against decreasing an existing line is:
```js
if (order.status === 'fully_paid') {
  // block decreases
}
```
This is a **string-status check**, and the order's `status` field was stuck at `deposit_paid` even though it was financially fully paid (see Bug C). Because the status string didn't say `fully_paid`, the guard never engaged, and the decrease went through freely.

The frontend has the *identical* flaw at `betaling/page.tsx:419`:
```js
const minQty = ['fully_paid', 'preparing'].includes(order.status || '') ? existingQty : 0
```
Same status-string dependency, same bypass.

**Fix direction (agreed with operator, not yet implemented):** Replace the status-string check with a check based on **actual completed payments vs. order total** (ground truth, immune to status-sync bugs): if total completed payments (deposit + remainder, in øre) already meets or exceeds the order's current `total_amount`, block any decrease to any existing addition line, regardless of what `order.status` says. Apply this in the API (critical, authoritative) and mirror it in the frontend stepper (defense-in-depth / correct UX — pre-populate `minQty` from `existingQty` unconditionally, not gated on status).

**Do NOT** just fix the frontend — the API is the real vulnerability; anything that calls this endpoint (including future UI, admin tools, or a buggy retry) can trigger the same data loss.

**Bug B (compounding, lower severity):**
`app/api/eggs/my-orders/route.ts:84-116` (the **list** route — NOT `[id]/route.ts`, which does not have this problem). Unconditionally calls `sendEggDepositConfirmationEmail(...)` for every order with a completed deposit, on every page load, with no check against `confirmation_email_sent_at` or the email dispatch queue. Only saved from being pure spam by the content-hash idempotency key — but any order content change (like Bug A's corruption) produces a new hash and re-sends. **Fix:** gate this send on `!order.confirmation_email_sent_at` (column already exists, added in the `20260624_payment_resilience.sql` migration from earlier this engagement) the same way the daily audit cron does.

**Bug C (contributing, pre-existing, may already be partially fixed):**
Order status was stuck at `deposit_paid` despite the remainder being fully paid on 06-25 — should have flipped to `fully_paid`. This is the same *class* of bug as the "Dataavvik" chicken-order bug fixed earlier this engagement, but in the egg line. **Note:** commit `a8323f67` (not mine, unreviewed) touches exactly this — `getEggDepositStatus(order)` usage in `my-orders/[id]/route.ts` — it may already improve this for some paths. Needs verification: does it cover the `additions` endpoint's own status derivation too? (Additions route has its own inline `nextStatus = remainderPaidOre >= nextRemainder ? 'fully_paid' : 'deposit_paid'` logic, separate from `getEggDepositStatus`.) Not yet checked for consistency between the two.

### What has NOT been done yet
- **No code fix applied.** All of the above is diagnosis only.
- **No remediation for Robert (EGG13063678).** Operator has not yet chosen between: (a) restore the missing 8 Cream Legbar + 5 Maran eggs if stock allows, or (b) refund the 623 kr difference. **Ask the operator before acting** — this is explicitly a business decision, not a code decision.
- **No scan for other orders hit by the same Bug A pattern.** Given the day-before add-more offer is a normal, scheduled, widely-used feature and the status-stuck bug (Bug C) is plausibly common, other customers may have silently lost paid-for eggs the same way. This should be run once Bug A is fixed (so a fix-verification pass and the historical scan can happen together): find all egg orders where `SUM(completed payments) > current total_amount` by a materially large margin, cross-referenced with an `egg_order_additions` row whose `created_at` is later than the order's remainder-payment date.
